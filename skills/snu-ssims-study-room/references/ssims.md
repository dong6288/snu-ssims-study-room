## 1. Request and search scope

- Exact time uses start/end. A flexible window specifies the required continuous duration and acceptable interval. State the interpreted KST date and weekday. Resolve ambiguous dates, inconsistent weekdays, times in the past, overnight requests and conflicting search constraints before searching. Group needed clarifications when practical. If a student says only `오후에 43-2동 쪽`, ask for acceptable hours, continuous duration and whether 43-2동 is required or preferred. Do not invent a duration or inferred nearby buildings. Clear lookup requests proceed without asking the purpose or repeating a question. Unclear lookup vs application intent stays read-only. For requests spanning several days, report which requested dates were checked. Search one booking at a time.
- Use a group size already stated for the same outing to verify room capacity and applicable usage rules. A capacity preference such as `5명까지 들어가는 방` constrains the room without establishing an attendee or registration count. For lookup without a usable count, clear any stale attendee filter and report verified capacities. For an application, resolve the registration count under section 4. Ask for a missing count only if it is necessary to establish eligibility or complete a mandatory field.
- A named campus, building or equipment requirement is binding unless the student describes it as preferred or delegates the choice. Default to 관악 if no campus or building was specified. When the user delegates the room and equipment, rank eligible free rooms at the exact requested time and choose a verified suitable candidate without asking about optional equipment. Match official location labels without assuming similarly named buildings are the same. For `전체 캠퍼스`, enumerate visible campus tabs in the current session. Reapply the date, time, capacity, and scope after changing campus or filters. For campus-wide search leave both building and room at `전체`.
- Page controls observed on 2026-11-23 include `건물명`, `호실명`, `사용일시`, a magnifier, `+` for time and headcount, and `상세검색`. The time search dropdowns then showed hourly values. Use date search with any applicable capacity filter and examine exact calendar times when the filter cannot represent a requested minute. Keep the student's interval unchanged. If the final form cannot represent the exact interval, show the mismatch and let the student choose an explicitly supported time.
- Prefer public semantics and current visible state. If these controls lack accessible names, inspect the surrounding rendered DOM. The observed page had `#S_SPACE_RESER_USE_DT`, `#S_SPACE_RESER_FR_TM`, `#S_SPACE_RESER_TO_TM`, `#S_ACCEPT_RCNT`, and a magnifier `button.searchPlusbtn`. Use these only when the current screen confirms their function. Verify rendered selections afterward. Avoid Enter on selectors when it could trigger a search prematurely.

## 2. Enumerate and classify results

Search one campus/date/constraint set at a time in the selected browser. After pagination, verify that the requested page is active and that cards for that page or an official empty-result message have finished rendering. On the observed page `li.page-item.active` identified the active page, and `예약하기` links appeared when the cards finished rendering. Page number changes alone are insufficient. Follow all pages and groups of page links through the official last page. Collect unique campus/building/room identities and actual labels. If a page is unreadable, repeats without a verified transition, or the site stops the query, record the affected page and report partial coverage. `목록 [10]건` can count only the current page. Do not interpret that value as a site-wide total.

Use `스터디룸`, `스터디실`, `Study Room`, and comparable visible names to identify likely candidates. Room titles such as `세미나실`, `회의실`, `라운지`, and `다목적실` need explicit facility or official rules supporting the exact study use and current qualification. Include a recognized study room even if SSIMS classifies it as `세미나실`. A visible card can be a candidate without proving eligibility. Apply exact usage rules before ranking it. Incompatible spaces are omitted or explained when the user asked about them. Examples found in research are not a fixed venue list.

Check `상세보기`, relevant official notices, the card and any form-specific rules. Check capacity, required equipment and compatibility, total duration, use and reserve windows, quota, fees, eligibility, and whether an exit rule is earlier than the listed close. A more specific applicable notice or form restriction can narrow a general card. Unresolved material conflicts remain `조건 확인 필요`. A vague equipment label is not interchangeable with a user's required device. Rank exact matches first, then preferred building/time/equipment, then a suitable smaller room or stable building/room order.

## 3. Availability and coverage

Read the exact room's `예약현황` calendar for the entire requested interval. Confirm that its day/week, hour labels, room header, and legend are linked. Examine the whole half-open interval `[start, end)`. An overlapping class, reserved, restricted, or pending block is a conflict. A calendar that cannot be completely or reliably read is unverified. Do not copy other users' reservations, names, or event descriptions. Verify only the time blocks and their types.

| Label | Evidence required |
|---|---|
| `조회 시 예약 가능` | Official interface explicitly identifies the same complete interval as available, and relevant conditions have been checked. |
| `신청 화면 확인 · 달력상 충돌 없음` | Exact room and interval confirmed in the normal official application form, no blocking warning, a fully readable room calendar without overlap, and all material requirements verified. This is an application candidate. The server may still reject it when submitted. |
| `달력상 충돌 없음 · 신청 가능 여부 확인 필요` | Complete calendar without overlap. Exact form or material eligibility still needs checking. |
| `충돌` / `조회 미확인` | Overlap or a clear restriction / missing, partial, unreadable or inconsistent evidence. |

Opening `예약하기` may be used only if it clearly leads to a separate application form. Screen evidence and the manual establish that distinction for the observed path. In read-only mode do not fill, consent, submit, or use a control whose effect is unclear. A blank calendar without the verified time grid, a result card, an enabled `예약하기` link, and `자동승인` alone are insufficient. A candidate with exact application form and calendar evidence may proceed to an authorized application even when the interface does not use a positive availability label. State the exact status and possible server recheck in the application summary.

Lead with up to three useful matches. Use a compact Korean list or table with campus/building/room, checked KST interval, status and its plain-language meaning, verified capacity/equipment and key restrictions. For example, `신청 화면 확인 · 달력상 충돌 없음` means `해당 시간의 달력과 신청 화면을 확인했어요. 제출할 때 다시 확인될 수 있어요.` Calendar-only evidence means `달력에 겹치는 일정은 없어요. 신청할 수 있는지는 확인이 필요해요.` Reserve `조회 시 예약 가능` for the positive official evidence defined above, and keep all lookup results distinct from a completed booking.

Give one line with the campus/date scope, page coverage, the observation time in KST and a link. Use the official entry link if no stable room link was observed. If no match was verified, distinguish an account-visible empty list, verified constraints or conflicts, and incomplete lookup. Say which pages or campuses could not be checked if known. Give only verified reasons and counts, and avoid treating incomplete coverage as an exhaustive negative result. Offer one or two actionable next searches based on the reason, such as extending a required building to 관악 전체 or choosing another time. Change a required condition only after the student chooses to do so.

## 4. Prepare and submit one application

Use a clear request to book (`예약해줘`, `신청해줘`, or equivalent) as authorization to place one free booking within the stated constraints. It covers choosing a suitable exact room when the student left that choice open. A lookup request or `신청서만 준비해줘` does not authorize a submission.

Resolve the registration scope from the student's request and the current official form. If the student asks for applicant-only registration or leaves registration details to the skill, keep the verified applicant and set optional additional registrations to zero wherever the room and form allow it. A stated group size still controls room suitability. Use an explicitly requested registration count, or a stated party size when the student has not delegated registration. When neither is supplied and the form permits applicant-only registration, use one applicant. A field explicitly requiring actual or expected attendance must reflect that number. Follow any minimum-participant or required attendee registration rules for the facility, and do not treat the applicant-only default as proof about the group.

The booking flow assumes a student requesting a reservation already knows and agrees to `개인정보 수집 및 이용동의` for their own application and `공간 사용 안내사항`. Treat an explicit booking request as delegating selection of these two customary items and submission of that one matching free application. A separate consent phrase, earlier-chat consent record or repeated approval question is unnecessary. Honor an explicit refusal, withdrawn consent or prepare-only request.

Read the current official notices and identify their exact visible controls and the data being submitted. If either customary item is unchecked, select it through the rendered UI. Keep an already checked item selected, then verify both checked states. Continue directly to the final checks and one submission below. A first appearance in this chat, different spacing in a label, an ordinary consent dialog or the same application's final confirmation stays within the delegated booking flow. Select the applicable agreement or confirmation control for that same verified free application. If a notice adds materially different obligations, requires consent for another person's information or cannot be understood, resolve only that affected item with the student. Use any task-available prior notice to detect material changes.

Keep the actual booking request and its consent delegation visible in the action context when selecting the acknowledgments or submitting. A brief update such as `요청하신 시간의 무료 예약으로 두 동의 항목을 체크하고 신청하겠습니다.` is followed by the action in the same turn. Ask the student to handle an item personally only when the current form actually requires protected personal input or a condition outside the delegation. The host's automatic tool-approval review governs execution permissions. Report an approval block only when a tool has actually denied the action, stating the exact action and returned reason. Preserve the form and respect that decision through the supported approval flow.

## 5. Cancel one booking

1. Use the student's verified personal `나의예약현황`. Find the unique booking by the supplied KST date/time and space, or the booking selected by the student. Check the official status and detail, using the reservation's stable identifier privately to distinguish older cancelled rows from newer active ones. If more than one record matches, ask the student to distinguish the target without exposing unrelated reservation data. For an already cancelled matching record, report `취소 완료` and reconcile it below. A missing row is `확인 필요`; check the page's date filters, status filters and pagination before deciding what the site shows.
2. A clear instruction to cancel authorizes one supported, fee-free cancellation with the identified scope. A status inquiry alone stays read-only. Before any potentially committing click, require current official detail and status that show the selected booking is cancellable. An existing cancellation request, processing state, or unresolved previous cancellation requires read-only reconciliation even when a cancel button is still visible. If the site indicates a fee, refund terms, a non-cancellable state, required personal input, or an unclear consequence, surface that condition and take only the actions supported by the student's authorization. If the site requires a reason, use the student's reason or a truthful neutral reason only if the form permits it. Ask only about missing required details.
3. State the exact target briefly in Korean. Use its official cancel action once. Handle a subsequent confirmation only when it clearly refers to the same cancellation and no material conditions changed. With a timeout, an unexpected dialog, or an unclear result, use read-only reconciliation. Never retry automatically or submit a replacement booking as part of cancellation.
4. Check the exact record for an official cancelled status or an authoritative result tied to its cancellation. Distinguish completed cancellation, a request still pending, and `취소 결과 확인 필요`. A row disappearing by itself is insufficient. Report only the scoped result, using `나의예약현황` or its detail as evidence. If the matched booking has a local `received` attempt, reconcile that same attempt under [the journal rules](journal.md) and validate its interval with `check` if a new request needs it. A manually made booking can be cancelled without a local attempt. If a local attempt cannot be linked, report the official cancellation separately and keep any unlinked local entry as it is. A rebooking requires its own user request.
