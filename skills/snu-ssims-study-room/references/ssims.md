## 1. Request and search scope

- Exact time uses start/end. A flexible window specifies the required continuous duration and acceptable interval. Resolve ambiguous local dates, inconsistent weekdays, times in the past, overnight requests, invalid headcounts, and conflicting constraints before searching. For requests spanning several days, report which requested dates were checked. Search one booking at a time.
- A named campus or building is required unless the student describes it as preferred. Match official location labels without assuming similarly named buildings are the same. Default to 관악 when unspecified. For `전체 캠퍼스`, enumerate visible campus tabs in the current session. Reapply the date, time, capacity, and scope after changing campus or filters. For campus-wide search leave both building and room at `전체`.
- Page controls observed on 2026-11-23 include `건물명`, `호실명`, `사용일시`, a magnifier, `+` for time and headcount, and `상세검색`. The time search dropdowns then showed hourly values. Use date and headcount search and examine exact calendar times when the filter cannot represent a requested minute. Keep the student's interval unchanged. If the final form cannot represent the exact interval, show the mismatch and let the student choose an explicitly supported time.
- Prefer public semantics and current visible state. If these controls lack accessible names, inspect the surrounding rendered DOM. The observed page had `#S_SPACE_RESER_USE_DT`, `#S_SPACE_RESER_FR_TM`, `#S_SPACE_RESER_TO_TM`, `#S_ACCEPT_RCNT`, and a magnifier `button.searchPlusbtn`. Use these only when the current screen confirms their function. Verify rendered selections afterward. Avoid Enter on selectors when it could trigger a search prematurely.

## 2. Enumerate and classify results

Search one campus/date/constraint set at a time in the selected browser. After pagination, verify that the requested page is active and that cards for that page or an official empty-result message have finished rendering. On the observed page `li.page-item.active` identified the active page, and `예약하기` links appeared when the cards finished rendering. Page number changes alone are insufficient. Follow all pages and groups of page links through the official last page. Collect unique campus/building/room identities and actual labels. If a page is unreadable, repeats without a verified transition, or the site stops the query, record the affected page and report partial coverage. `목록 [10]건` can count only the current page. Do not interpret that value as a site-wide total.

Use `스터디룸`, `스터디실`, `Study Room`, and comparable visible names to identify likely candidates. Room titles such as `세미나실`, `회의실`, `라운지`, and `다목적실` need explicit facility or official rules supporting the exact study use and current qualification. Include a recognized study room even if SSIMS classifies it as `세미나실`. A visible card can be a candidate without proving eligibility. Apply exact usage rules before ranking it. Incompatible spaces are omitted or explained when the user asked about them. Examples found in research are not a fixed venue list.

Check `상세보기`, relevant official notices, the card and any form-specific rules. Check capacity, required equipment and compatibility, total duration, use and reserve windows, quota, fees, eligibility, and whether an exit rule is earlier than the listed close. A more specific applicable notice or form restriction can narrow a general card. Unresolved material conflicts remain `조건 확인 필요`. A vague equipment label is not interchangeable with a user's required device. Rank exact matches first, then preferred building/time/equipment, then a suitable smaller room or stable building/room order.

## 3. Availability and coverage

Read the exact room's `예약현황` calendar for the entire requested interval. Confirm that its day/week, hour labels, room header, and legend are linked. Examine the whole half-open interval `[start, end)`. An overlapping class, reserved, restricted, or pending block is a conflict. A calendar that cannot be completely or reliably read is unverified. Do not copy other users' reservations, names, or event descriptions. Verify only the time blocks and their types.

| Label | Evidence required |
|---|---|
| `조회 시 예약 가능` | Official interface explicitly identifies the same complete interval as available, and relevant conditions have been checked. |
| `신청 화면 확인 · 달력상 충돌 없음` | Exact room and interval confirmed in the normal official application form, no blocking warning, a fully readable room calendar without overlap, and all material requirements verified. This is an application candidate. The server may still reject it when submitted. |
| `달력상 충돌 없음 · 신청 가능 여부 확인 필요` | Complete calendar without overlap. Exact form or material eligibility still needs checking. |
| `충돌` / `조회 미확인` | Overlap or a clear restriction / missing, partial, unreadable or inconsistent evidence. |

Opening `예약하기` may be used only if it clearly leads to a separate application form. Screen evidence and the manual establish that distinction for the observed path. In read-only mode do not fill, consent, submit, or use a control whose effect is unclear. A blank calendar without the verified time grid, a result card, an enabled `예약하기` link, and `자동승인` alone are insufficient. A candidate with exact application form and calendar evidence may proceed to a user-approved application even when the interface does not use a positive availability label. State the exact status and possible server recheck in the preview.

Show up to three useful matches with campus/building/room, checked KST interval, status, verified count/equipment and any applicable restrictions, plus observation time. Include campus/date scope, page coverage, and partial/empty/failed states. Use a generic official entry link if no reusable stable room link is observed. Distinguish account-visible search with no results from all rooms being occupied. Never present cross-campus or cross-account completeness beyond the checked result sets.

## 4. Prepare and submit one application

1. Confirm the exact permitted room and KST interval. Open the official application form via `예약하기`. Verify the official form distinguishes `예약신청하기` and that the displayed room and times are correct. If the site presents a different or ambiguous flow, show the student the page and stop before any possible submission.
2. Fill actual purpose, title and content into the official form. Let the student enter participant identities/authentication and review/check required consents in Chrome. Read the resulting total from `총 인원수`; an adjacent `참여자 수` selector is not proof of a total. Verify the application cost and approval/entry conditions. Use assisted manual completion for paid, payable, or unverified-price forms, no payment automation.
3. Check the student's scoped `나의예약현황` before the approval preview. Record only the matching row identifiers or times needed in the task context as a baseline. Use a read-only official tab if checking would discard the original form. An overlapping prior booking, ambiguous prior attempt, or unreadable existing records must be resolved before automated submission. Do not read department or third-party booking details.
4. After the student has finished their input, show the exact campus/building/room, date and start/end KST, total, purpose category, title, body, cost, and material conditions. Get explicit approval for this completed form. Recheck the official URL, same Chrome profile/account/qualification/tab/form, all approved values and current evidence. An intervening login, user form handoff, scope change or replacement form requires a new preview and approval. Stop if exact interval evidence or other material conditions cannot be rechecked.
5. Run `claim` from [the local journal](journal.md) immediately before the first potentially committing click. Only a valid fresh `claimed` result on this run is authority to proceed to the official `예약신청하기` after the student's approval. A journal result is not an official booking. Do not replay `claim` to acquire permission after an uncertain result. If the first action opens an unmistakably pre-submission official confirmation showing the same approved application, follow applicable browser confirmations for that same attempt. Stop at unknown dialogs or changed details. In a new chat reconcile the earlier attempt and do not take a second committing action until its outcome is resolved and a new exact application is approved.
6. Use an official response directly tied to the click, or a newly identifiable matching reservation row (for example a new reservation number) compared with the pre-click baseline. Translate a specific status only when that evidence supports it. `자동승인` is a facility setting, not an outcome. If there is an unambiguous official rejection before acceptance of the application, report `미접수`. A later official `반려` or `취소` of an identifiable received application releases its journal block once settled as `denied` or `cancelled`. On timeout, interruption, apparent success without matching evidence, stale list, or delayed row, report `결과 확인 필요` and leave the journal blocked. An empty list does not prove nonreceipt. When the official evidence is conclusive, settle the same attempt in the local journal. Share only the scoped receipt, status, and actionable access/exit information with the user. Use the host's proof and confirmation controls without exposing identities or unrelated records.
